# Browser role composition

`web.cpp` is compiled for server, client and Workshop roles. It composes Application, presentation and the appropriate lobby/session contracts; host-only imports remain conditional. The threaded server path owns background authoritative pumping, while client/Workshop stay free of simulation implementation dependencies.

Frame timing comes from `phoenix.diagnostics.browser_profile`. Only the threaded server supplies the optional background-metrics callback. Disposable Workshop testing uses `phoenix.workshop.browser_test_client`, a worker request/feedback adapter; the worker host is a separate executable. EM_JS callbacks in this entry point remain platform composition glue.

Ordinary and threaded WebAssembly are separate build/runtime gates. Preserve exported callbacks, worker queues, shared-memory requirements and event/frame ordering. Browser rendering, device, accessibility and performance journeys require explicit smoke evidence; compiled exports alone do not establish them.

`phoenix_browser_host` is built with the ordinary browser server. When a split DAT release is selected, the launcher starts the lobby from the lobby DAT and transfers the mission archives to the worker after the first game frame. The worker owns the production lobby, verifies and attaches the archives, prepares the World and handles admitted commands. The page owns input and rendering. It consumes presentation assets and the session's projections through its `SessionPort` adapter. The existing browser WebSocket and WebRTC adapter runs on the page and forwards transport events to the worker. Ordinary WASM uses independent memories.

The published launcher selects the split base by default. Legacy archives, recovery launches and scenarios outside the public lobby catalogue use the existing content path. Lobby introductions carry the text and system labels used by the lobby, with full authored help available in the Console presentation.

The 3 November 2026 Chromium game smoke used the production Rescue release and a loopback signalling service. With isolation disabled, the worker confirmed non-shared memory. The 2.7 MB lobby DAT supplied the Cruiser roster while the 91.5 MB mission DAT was delayed at the HTTP server. Settings opened and closed during preparation. A second tab exchanged direct WebRTC packets, claimed Helm and readied up. The host drew the Viewscreen and advanced the World. The remote All stop command slowed the Cruiser from 16 m/s to zero, confirmed by both tabs. The two-tab run recorded 6,983 animation callbacks through launch and a longest callback gap of 934 ms.

A follow-up Chromium trace reproduced a 933 ms gap on the first frame that applied the mission theme. Fourteen sliced styles referenced the same control bezel, and applying the theme decoded that image for each style to obtain its dimensions. A diagnostic run without the theme isolated that cost. The renderer now registers and measures each distinct artwork reference once per application. With the full authored theme enabled, the same two-tab Rescue run recorded a 200 ms gap at that transition and a 433 ms maximum from worker startup through launch. The remote Helm again claimed its seat over direct WebRTC and stopped the Cruiser, with both tabs reporting zero speed. The host worker reported independent memory.

The next trace reproduced the 433 ms gap during graphics startup before the first lobby frame. Menu initialization decoded bundled PNGs to check dimensions and decoded the panorama again when building the flash overlay. The dimension checks now read the PNG header, and panorama upload and flash composition share one decode. With the same Rescue archive in Chromium, graphics startup took 160 ms versus 357 ms before the change. The corresponding frame gap and the maximum through launch were both 250 ms. The host ran without shared memory, accepted lobby input during preparation and exchanged direct WebRTC packets with the remote Helm.

A follow-up trace reproduced a 236 ms task that combined lobby setup with 146 ms of graphics startup. Ordinary hosting now yields a browser paint before graphics initialization and passes the launcher catalogue directly to the worker. Chromium traced separate tasks for lobby setup and graphics. The two-tab Rescue rerun still peaked at a 284 ms frame gap, with 272 ms of script in the first game frame. The original combined task was split, but the peak frame gap remains unresolved.

To run the [worker smoke](../../../tests/manual/browser_host_worker.html), build `phoenix_browser_host` with browser threads disabled into a `wasm` subdirectory of a scratch site. Package `content/test` as `test.mission.dat` at the site root using `phoenix_pack`. Extract `launcher.json` from `test.lobby.dat` as `metadata.json` and copy the smoke page as `index.html`. Serve the site over loopback HTTP without isolation headers. Open the page, start attachment, and exercise the page input button while the worker prepares.

The 3 November 2026 Chromium smoke used the 20,360,184-byte test mission. The browser reported no shared memory. The worker accepted a Console claim before download, rejected an invalid archive, retained the claim after valid attachment and advanced the World. The page accepted one input while preparing and recorded 187 animation frames during the 3.11 seconds from download to readiness. The largest reported frame gap was 17 ms through the first tick. This evidence covers the standalone offline worker.
