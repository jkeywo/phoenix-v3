# Lossless DAT image benchmark

Run `./tests/manual/image-codecs/run.ps1` from the repository after bootstrap and native configuration/build have populated `build/native/_deps`. The Windows script builds a native Release executable and an Emscripten Release executable from the same source. The standalone benchmark pins libwebp and uses the game's existing miniz, stb and JSON dependencies. It is manually invoked evidence, with no timing assertions.

All PNGs recursively under `content/base/assets` are read without modifying them. Native and WASM each encode an independent ignored corpus under `build/image-codec-bench/corpus` and `corpus-web`. The script compares every decoded source pixel and encoded WebP record between native and WASM, then decodes the native corpus in WASM for the shared-input timing comparison. The alternatives are RGBA plus ZIP level 1 (the previous DAT representation), RGBA plus ZIP level 9, PNG with row filtering and miniz level 9 (retaining the original PNG when smaller), and exact lossless WebP (method 6, quality 100). An adaptive comparison selects the smaller PNG/WebP entry per image. Each candidate is an independent ZIP entry; WebP includes the production 16-byte image header. PNG and WebP entries are stored without another compression pass.

Both executables decode the identical corpus three times. Each timed interval includes ZIP extraction, decoding and RGBA allocation/copying; file I/O and byte comparisons are outside the interval. Every decoded pixel and dimension is compared with the reference RGBA bytes on every pass, including transparent RGB. A mismatch fails the run. The WASM executable runs in Node/V8 with raw filesystem access; this measures the C++ WASM codec, not browser rendering or network latency. `native-results.json`, `web-results.json`, `corpus/encoding.json` and the path/dimension manifest are the receipts. These are measurements of the current assets, not production content goldens.

PNG filtering uses stb_image_write's row selection with miniz compression rather than its built-in compressor. Both WebP builds disable SIMD and threading, matching production identity requirements. High encoding effort is intentional; packaging time is reported separately from loading time.
