# Peer replication

`phoenix_replication` owns a C++ Raft-style fixed-roster actor, independently of graphics, transport, the signalling service and the simulation. Each participating ship server will run this actor and the same full-world simulation. There is no central membership arbiter. Remote application wiring is still pending.

The actor implements pre-vote, persisted terms/votes, majority election, a current-term no-op barrier, bounded append batches, matching-prefix checks, conflicting uncommitted suffix replacement, majority commit, check-quorum step-down and replay of the durable committed prefix. A disconnected stale peer cannot increase other peers' terms simply by probing for an election. The roster and session epoch are fixed and bound into durable state; returning identities can catch up, but this actor does not add new members during play.

The application must bind incoming message senders to established peer identities. The actor rejects unknown/mismatched senders, session/recipient mismatches, malformed counters and oversized packets before mutation. This is crash-fault consensus, not Byzantine consensus or a substitute for transport authentication.

Storage is asynchronous. `pending_write()` returns a generation and incremental durable transaction: term/vote/commit metadata, the retained log-prefix length and only changed suffix entries. Only `persisted(generation, true)` releases messages dependent on that transaction and makes its committed entries available for execution. Stale completions do nothing; a failed write stops authority. Gameplay consumes `take_committed()`, never a volatile log, a wall-clock tick or the leader role alone. A restarted actor replays its committed prefix; the caller must rebuild execution or align that replay with a verified simulation checkpoint.

Synthetic native and WASM integration cases exercise delayed storage, failed storage, elections, bound sender identities, majority-only application through production World admission/ticks, three-peer partition/replacement/catch-up, rejection of a conflicting minority frame, durable restart and two-peer pause after one loss. They compare current controlled replicas rather than a frozen production hash. This establishes the actor's tested scenarios, not a formal proof or completed network acceptance.

`phoenix_persistence` supplies actual durable adapters. Windows appends SHA-256 checked journal records on a worker thread, holds an exclusive writer handle and waits for `FlushFileBuffers` before reporting success. Restart validates complete records and truncates only an incomplete unacknowledged tail; corrupt complete records fail closed. Browser storage appends the same opaque C++ records in strict IndexedDB transactions and reports success after transaction completion. A Web Lock excludes another live tab for the same namespace and remains held until pending transactions finish. Missing strict durability or exclusive locks is a refusal, not an in-memory fallback. Transaction reconstruction validates identity, monotonic terms/votes and immutable committed prefixes.

Each journal is bounded to 128 MiB and each transaction to 2 MiB. The current log supports 131,072 entries. Exhaustion refuses further acknowledgements; automatic checkpoint/compaction is pending. Browser-origin eviction or user-cleared storage must never be treated as an existing peer identity with an empty log. Returning-peer admission will have to verify the expected durable identity and catch up before service.

Native automatic integration exercises asynchronous completions, exclusive writers, backpressure, restart, incomplete tail repair and corrupt-record refusal. The separate browser smoke probe (`storage-probe.html?key=...`) tests actual IndexedDB; its reload action requires an existing committed record. See [durability evidence](smoke/peer-storage.md). Storage smoke is separate from the headless Node/WASM gate.

`phoenix_fleet` composes this actor with authenticated transport and durable stores. A fixed roster verifies identical setup fingerprints before committing its initial barrier. Only a durable current-term barrier grants leader authority. Ordered presence changes record absent peers and fresh returning incarnations; stale-incarnation requests cannot regain authority. Real native multi-process integration exercises majority continuation, minority pause, two-peer pause, returning peers, exact replay, content mismatch and lost-journal refusal through production World execution.

The private server runtime persists the exact initial setup bundle and server profile, seals the expected journal before allowing network authority, and holds an exclusive identity lock. Recovery verifies the original bundle, identity, roster and content before replay. A missing expected journal fails closed. These bundles contain fleet credentials and are rejected as ordinary gameplay packs; they are not client content downloads.

Remaining integration: connect this runtime to playable host/client lobbies and station admission, add automatic checkpoints/compaction, fleet snapshots and portable recovery, and establish mixed native/browser fleet evidence. Playable applications currently still use singleton consensus and do not claim fleet play.

Platform contracts: [IndexedDB transaction durability](https://developer.mozilla.org/en-US/docs/Web/API/IDBDatabase/transaction), [Windows FlushFileBuffers](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers).
