# Network play

Hosts expose authored Console seats with independent leases. Approve each first-time crew or GM connection in the host lobby; reconnecting credential holders retain approval. Ordinary crew download a verified own-ship presentation bundle, containing layouts, images and display limits, rather than authoritative packs. Only live permitted radar contacts cross the observation boundary. Approved GM connections retain the full read-only inspector.

The native [main menu and pre-game lobby](native-menu.md) now coordinate ship-slot selection, approval, automatic setup transfer and a five-second readiness countdown. Mandatory AI ships are simulated by every host without additional server votes.

For the existing manual setup route, **Export fleet setup** creates a private bundle for the authored ship slots. Load that bundle on each server, select a distinct `shipN` member in the recovery lobby and resume. Crew invitation codes use the member's `-console` endpoint. The existing durable fleet driver orders the same Console claims, commands and ticks used by singleton play. Reloading the same bundle/member/profile reconstructs its original journal; committed server absence releases only that server's Console claims. Saving an active fleet produces a portable bundle at a tick boundary with a fresh session epoch and key; it carries no peer term/vote state or client credentials.

The four applications now share C++ session admission, verified content transfer and permitted projections. Run the signalling service described in [network setup](network-transport.md), then serve `build/web` over HTTP on loopback or HTTPS on a public host. Public signalling requires WSS; no public service is deployed by this repository.

Native starts a ship server by default. Import ordered packs and start a mission through Home, or pass `--game-pack path.zip --mission map.id --slot slot.id --ship ship.id`. New pre-game lobbies show a six-character uppercase alphanumeric Join Code and its QR invitation. Existing `room/server` invitations remain supported. `--service`, `--profile` and `--data` select the service URL and local storage namespace. `--local-only` preserves the offline adapter for manual smoke captures.

[Join forms and QR invitations](joining.md) are available in C++. Browser hosts prefill their launcher URL; native accepts `--page` or an entered page address. Scanning a QR opens ordinary client/GM admission.

Join from another native application with `--client --code room/server --service ws://127.0.0.1:9080/phoenix`, or select Console in the HTML launcher. Select Workshop / GM and GM inspector, or use native `--gm`, for read-only inspection. Use distinct local profile names for independently operated clients on the same machine/origin. Browser roles use the same `code`, `service` and `profile` parameters. `slot` remains a launcher hint; this version operates the host's selected ship slot.

The client persists its identity/credential before readiness, checks its persistent archive cache, transfers its verified presentation bundle and runs the production content verifier. It explicitly selects an available authored Console on its own ship server. Local and remote operators can claim different Consoles independently. Operating requests address Console Controller command channels and pass through capability, effective operator/generation, lease, sequence and quorum checks; only durably committed tick frames execute. Player traffic contains the claimed ship and permitted radar contacts. Approved GM traffic contains full authoritative inspection, displayed in docked map, entity and property panels. GM cannot submit operating commands or edit the world.

Disconnected stations expire after three seconds without application heartbeats. Another operator must confirm replacement, which creates a fresh committed lease. The original persisted identity can reconnect to its own reservation; reconnecting discards queued inputs and renews the lease before control resumes. Clients wait for their own server rather than migrating authority. Runtime ZIP export and paused recovery remain server operations.

The public hello carries a nonce-bound nested proof when the client has a stored credential. An existing server requires that proof to resume its known identity; a fresh server epoch can issue a new credential without accepting the previous game's authority. The real-process regression also restarts the host and reconnects the persisted client profile to a newly started game.

Both singleton and fixed-roster fleet sessions are playable. Hosts automatically compact committed history and catch up returning members from checkpoints plus a suffix; see [replication](replication.md). Crew and approved-GM projections transfer as bounded, hash-verified snapshots, with four outstanding 12 KiB chunks, retries and acknowledgements. Clients publish only complete snapshots; the per-connection stream identity discards delayed packets after server restart. Each snapshot is limited to 4 MiB. Multi-server native/browser interoperability and six-screen performance remain manual acceptance criteria.

`scripts/check.ps1` includes a synthetic real-process host/client/GM journey through the signalling service, verifying content, actual movement, filtered contacts, host approval and confirmed replacement. The fixture is independent of shipped tuning. Actual browser journeys are recorded in [network play smoke evidence](smoke/network-play.md).
