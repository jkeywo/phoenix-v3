Phoenix V3 · Manual performance evidence · 24 October 2026 · 30-minute investigation

Console preparation and simulation projections dominate

The measured native and WebAssembly workloads miss the 60 Hz target. Start with Engineering Console preparation, then reduce repeated observation construction in simulation and presentation.

These captures use Rescue under threat, the authored rescue Courier and delivery Cruiser, and the production content loader, local session, fixed ticks and renderer. They measure the mission opening with default complexity and AI for unclaimed seats; there is no scripted human input.

1. Engineering preparation is the largest measured frontend cost

Corrected full-framebuffer confirmation: 5760 x 2160, five active Consoles plus one Viewscreen, 16 measured frames: mean frame interval 3115.09 ms (0.32 FPS), Engineering layout/preparation 1629.61 ms and Engineering projection 296.36 ms per frame. The framebuffer image was inspected with all six regions visible. This confirms the hotspot at the intended pixel workload; physical six-monitor scanout remains untested.

The initial native five-Console capture averaged 1,612.65 ms per frame in Engineering’s console/2/layout bucket and 290.44 ms in its projection bucket. Total preparation was 2,040.29 ms and the following Console rendering/update stage was 370.91 ms. This capture had five claimed Consoles but Windows clamped its framebuffer to 3844 × 1181; it diagnoses CPU preparation, not the full six-display pixel workload.

src/presentation/consoles.hpp:1837 prepares each surface every frame. Its “layout” timer covers much more than RmlUi layout: readouts, controls, authored placement, updates and semantic geometry. src/presentation/authored_layout.hpp:394 reapplies the authored tree and calls context_->Update() several times. The separate before/after-widget timers do not cover all these updates.

Next action: subdivide this bucket around authored styling, each internal RmlUi update, control/readout generation and geometry measurement; cache unchanged structure, properties and geometry. Virtualise long Engineering collections. Retain current semantic values and authoritative command admission.

2. Simulation builds expensive observations every tick

The first refined native Cruiser block spent 56.78 ms per tick constructing Console observation snapshots, already beyond the entire tick budget. Controller execution added 23.15 ms, craft/docking preparation 16.91 ms, equipment 14.20 ms and Comms/boarding/craft refresh 14.18 ms. These are sequential phase means from the same 200-tick block, including initial warm-up; use the selector below for all available blocks aggregated per run.

src/simulation/world.cpp:2784 captures observations for every entity’s authored Consoles. The Controller execution loop later excludes departed/dormant craft, but the snapshot loop has no equivalent filter. src/simulation/console_observations.hpp:119 constructs combat, processors, logistics, docking, sensors, per-system telemetry and contacts. This identifies a concrete repeated-work path; the saving from any particular cache/filter remains unmeasured.

Next action: count requests and generated rows by ship, Console and subsystem; avoid unnecessary dormant-craft work where its behavior contract permits; share immutable per-tick sensor/telemetry intermediates while preserving each Console’s permitted view.

3. Presentation repeatedly requests rich observations

Even one native Cruiser Helm Console averaged 36.04 ms per frame in projection and 13.50 ms in the broader layout bucket. The corresponding Courier means were 9.66 and 9.24 ms. Those costs recur at presentation frequency in addition to simulation snapshots.

src/core/console.cpp, ConsoleModel::refresh, asks the session for its observation. World::observe_at in src/simulation/world.cpp reconstructs many rich JSON boards, including logistics and docking boards already produced by capture_console_observation. Other screen paths also request observations. This is source-backed evidence of repeated construction, not a measured count of identical calls.

Next action: introduce revision-aware presentation projections keyed by tick, claim/generation and relevant local changes; reuse them across renderer and semantic consumers. Keep claims, UI navigation and command-feedback changes responsive between ticks.

4. Catch-up magnifies expensive ticks into multi-second frames

The runtime accumulates elapsed time capped at 250 ms, then runs 50 ms ticks. Once a Cruiser tick exceeds 50 ms, subsequent frames can execute five expensive ticks before drawing. The single-Console native Cruiser averaged 782.49 ms in poll/tick per frame against a 156.39 ms individual tick mean. The measured symptom is both missed frame cadence and simulation running slower than wall time.

Next action: reduce tick cost first, then evaluate an explicit catch-up budget and presentation scheduling. Preserve committed tick ordering and deterministic execution; dropping authoritative ticks would change game behavior.

Web-specific evidence

Incomplete workload: the five-Console 5760 x 2160 browser capture timed out 180 seconds after graphics became ready. It emitted no final frame report; no FPS or percentile is inferred for it. The three single-surface browser captures completed.

The browser runner collects 1 ms CPU samples from the actual WebAssembly runtime. In the Courier Console run, allocation/free routines accounted for about 10.77% of sampled self time, JSON lexer work about 5.06%, stream_fields() about 3.14%, and the generic wasm-to-js transition frame about 17.86%. These support investigating allocation-heavy JSON construction and runtime glue. Generic transition frames do not by themselves establish which compiler option should change.

The browser reports a visible document and NVIDIA RTX 5090 through ANGLE/D3D11, rather than a software renderer. It is headless Edge 156 on this Windows machine. It is not a physical phone measurement or a hosted-network latency result. RmlUi reports existing CSS syntax warnings; the favicon 404 is unrelated to runtime frame cost. No JavaScript page errors were reported by completed captures.

Method, environment and limits

  • Machine: Intel Core Ultra 9 275HX, 24 logical processors; NVIDIA RTX 5090 Laptop GPU; native NVIDIA OpenGL 3.3, driver 617.14. Browser GPU and version appear in the JSON.
  • Source: starting revision 4bf9f0147d5ebf97e8847e03bdbf22bab5fa5e3b plus the existing working-tree edits and opt-in diagnostic instrumentation. This was a shared, dirty checkout, not a clean release benchmark. Content archive identity is recorded in the JSON. The investigation did not modify V2 or change gameplay rules.
  • Build: native MSVC Release; Emscripten 6.0.12, libraries compiled at Release -O3 and diagnostic final link/wasm optimisation -O2 with function names retained. Exact native/web speed ratios should not be generalised to shipping builds.
  • Capture: graphics prepared before simulation starts; then 20 warm-up frames, followed by up to 600 frames or 45 seconds, whichever completes first. Frame deadline checking happens at frame boundaries. This diagnostic isolates loaded gameplay; it does not time menu, verification, downloads, lobby or asset-loading duration.
  • Timing: CPU wall time around production calls. Frame intervals include OS/browser scheduling; end-of-frame includes any presentation wait. GPU timestamps, GPU utilisation and VRAM were not measured. A small CPU scene-submission bucket cannot certify GPU headroom.
  • Scope: local authoritative simulation, Viewscreen and player Consoles. No fleet transport load, remote clients, Workshop/GM authoring workload, sustained combat, whole-mission progression, memory-leak/long-run test or real six-monitor scanout was profiled. There is no 60 Hz acceptance pass.
  • Variability: one final run per configuration, evolving scenario state and different tick counts; some build work occurred around native measurements. These establish large hotspots, not small optimisation deltas. Repeat on an otherwise idle machine before attributing small differences.

Validation

The native and WebAssembly manual diagnostic builds succeeded. The native simulation integration case passed motion, admission, radar, collision pairs and state-tree save/resume with the instrumentation present and disabled. Completed capture screenshots were inspected. No full integration gate or physical-device acceptance is claimed.
