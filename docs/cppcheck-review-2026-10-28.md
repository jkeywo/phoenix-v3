# Cppcheck review — 28 October 2026

Cppcheck 2.22.0 checked 819 first-party source, interface and header files under `src/`, `tests/` and `tools/`, using C++20, the Win64 platform, eight workers and `warning,style,performance,portability` checks at the normal analysis level. References, dependencies and generated output were excluded.

The direct scan took 11.71 seconds and rejected all 231 module interfaces. A second scan of temporary copies blanked module/import declarations and removed leading `export` keywords while retaining line numbers. It took 20.18 seconds and reported 2,714 diagnostics: 13 parser errors, 165 warnings, seven performance suggestions and 2,529 style suggestions. These are single-run tool times, excluding setup and copying.

Neither scan resolves imported module definitions or uses the native compilation database. The compatible scan is useful for finding candidates, but its diagnostic count is not a defect count or a complete safety assessment. Original XML, timing receipts and findings are retained locally under `build/cppcheck-2026-10-28/`.

## Validation

- Repeating the same 819-file compatible cppcheck scan took 10.50 seconds. Warnings decreased from 165 to 158 and performance suggestions from seven to five; style suggestions (2,529) and parser errors (13) were unchanged. All seven missing-initializer diagnostics rooted in `BodyView` disappeared, as did the two production copy suggestions. No cross-run performance improvement is inferred from the elapsed time.
- Clang-format checks passed for the three changed production files and the added sensor-test lines. Prettier accepted this report, and `git diff --check` passed for these changes.
- Native and WebAssembly builds were attempted. Concurrent workspace edits caused native compilation to fail at the new `ScreenDevices` use in `application.cppm`; the WebAssembly compiler crashed while compiling the same application interface. Further focused attempts encountered locked compiler output (`.obj` and `.pcm`) while other builds used the shared directories. Attempts to isolate the test executable still triggered shared CMake regeneration. These failures do not establish a regression in the reviewed fixes, but they prevent claiming completed build/integration validation.
- The new sensor regression has **not been executed**. Once the shared workspace builds settle, rebuild `phoenix_sensors_tests` and `phoenix_swept_collision_tests`, run the native sensor/directed/collision cases, and run the corresponding WebAssembly sensor/collision executables from `build/web`. The broader native suite remains a useful final gate for the shared contracts change.

Source review and static analysis do not establish physical-device, graphical, accessibility or performance acceptance.
