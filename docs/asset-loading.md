# Packaging and loading assets

Workshop's **File > Package…** menu exports a **Game pack** or the **Selected scenario**, as **Source ZIP…** or **Compiled DAT…**. Packaging runs inside native/browser Workshop; authors do not need a separate executable. Exporting leaves the ordinary Save destination unchanged. Native uses a save picker and writes companion files beside the chosen archive. Browser Package exports a `.bundle.zip` containing the archive and its companions; unpack it before publishing. Ordinary single-file saves/exports still work through full-archive or host-transfer fallback.

ZIP retains editable JSON and PNG files. DAT uses the `PHXDAT1` version signature followed by a bounded ZIP directory with entry CRC checks. `definitions.json` contains a `PHXCBR1`-prefixed CBOR record; PNG paths contain `PHXWEBP1` records: little-endian dimensions followed by exact lossless WebP pixels. These already compressed records use ZIP storage without a second compression pass. Source PNGs remain unchanged. The decoder accepts only the current compiled image version; old DAT artifacts must be regenerated. Logical asset references stay the same. Text manifest and launcher metadata remain available before WASM starts. Packages retain the 32 MiB transfer limit; DAT entries permit a full 16-megapixel RGBA image and the expanded package is limited to 256 MiB. Unsupported versions, damaged entries, invalid dimensions and excess bounds are refused.

Both encodings use the production verifier and exact archive SHA-256 identities. Workshop opens DAT as editable definitions/images; ZIP export restores JSON/PNG. Native `--game-pack` and `--workshop-pack` also accept source directories. A directory opened in Workshop uses Save As for its first saved archive. Browser imports accept ZIP or DAT. Installed-library filenames are internal storage keys and do not determine encoding. Saves and transfers retain exact loaded package bytes.

A scenario export is a small overlay with a distinct generated ID, a dependency on the current game pack, and an explicit override for the selected map. Package/install the game pack first, then its scenario. Shared definitions and images come from that prerequisite. The scenario's launcher metadata lists the selected map.

## Published companions and menu readiness

CLI packaging and Workshop Package use the same generator for ZIP and DAT. `<archive>.menu.json` has `schema: 1`, `sidecar_version: 1`, archive ID/hash, parent/dependencies, explicit overrides, root presentation settings, mission/slot/default-ship/name metadata and ship names. It contains no simulation definitions or gameplay images. Its `clients` array names `<archive>.clients/<ship-key>.dat`, with each DAT hash and exact ordered source identities. ZIP entries use deterministic timestamps so identical resolved inputs produce reusable client hashes. The DAT itself records its ship and source identities.

The menu reads these hints first. Full loading and production verification begin after the menu is interactive. Entry waits for the current enabled selection only when work remains; changed selections cannot publish stale results. Successful downloads and verification are reused. Errors prevent entry and preserve stored archives; return to the menu and retry entry after correcting the source. Workshop waits for its archives and save recovery verifies the save's embedded exact content. Player joins do not wait for unrelated gameplay packs. Missing or invalid metadata is derived through the production full-archive loader and stored beside installed archives.

## Preparation before play

Host preparation follows resolved references from the selected map through every allowed ship, fitted definition, Console, tree, situation, spawn group and image. It includes future literal spawns and explicitly declared dynamic dependencies. Unrelated scenarios' assets are omitted. A map can declare `"preload": ["my-pack.extra-ship", "my-pack:assets/extra.png"]`; references must resolve. Dynamic entity selection requires this declaration. Authors must include every possible dynamic selection; with an explicit preload list, runtime spawns outside the resolved definition set are refused.

Preparation decodes images on native workers (and threaded WASM workers), then uploads textures and prepares sprite materials on the graphics thread, yielding between resources. Ordinary single-threaded WASM yields between individual decode/upload steps. Texture owners share identical image payloads and retain immutable decoded pixels for material validation, mipmapped uploads and CPU sampling. RmlUi shares prepared premultiplied UI textures. Scenario resources remain retained for later spawns and are released with their owner.

Each Console prepares its ship's public presentation dependencies independently of scenario scenery. A host showing only Consoles does not prepare an unused 3D scene. Resource readiness is keyed by exact ordered pack identities, ship and scenario requirements, separately from session generation. Lobby activation, claim changes and a temporary missing snapshot do not discard matching prepared resources.

Authenticated lobby configuration and running-server offers may advertise a whole-ship DAT with its ship ID, hash, exact ordered source-pack identities and published URL. Clients reuse a matching cache or try that URL, verify the DAT and its presentation content, and carry prepared data from lobby into play. All public Consoles, including auxiliary Consoles, are present, so switching Consoles on that ship reuses the package. Claim permissions and observation filtering remain authoritative on the host. Different ships or effective content require a matching package.

Missing, corrupt, stale or browser-blocked downloads fall back to authenticated host transfer. The host loads full gameplay packs and generates the required ship DAT, including any scenario-specific loading artwork. The client does not download simulation packs for this fallback. Detailed hull graphics, world state, maps and private trees are excluded. Older offers retain host transfer. New ship servers and authorised GM clients retain their full-content requirements; player runtimes remain independent of simulation services.

Loading progress belongs to the display waiting for content. Menus, lobbies and Viewscreens retain their current presentation with a local progress card; a Console without ready content uses a placeholder within its own display. Ready displays continue rendering, routing input and publishing accessibility controls. There is no loading return that skips the rest of the spanning window.

Loading actions carry a display and request ticket. Cancel/retry affects that preparation only; cancelling a Console never leaves the shared session. Failed preparation reports a local error and retry action. Superseded results and actions cannot publish into a newer request. Existing content remains usable while its content identity and command authority remain valid; revoked controls and private observations are removed through the ordinary fresh projection path. Switching between already prepared Consoles on the same ship needs no new asset load.

Runtime progress preserves the screen's existing artwork instead of replacing it with a separate loading backdrop. The HTML launcher retains its startup background/progress display before WASM can draw. Pack/scenario loading artwork remains authored and transported in the presentation package.

## Lossless image packaging

The pinned libwebp 1.6.0 encoder uses lossless mode, `exact=1`, method 6 and quality 100. It preserves every decoded RGBA8 byte, including RGB under fully transparent pixels; no near-lossless preprocessing, quantisation or chroma subsampling is used. Each newly encoded image is decoded and compared with its source pixels before export. A bounded 32 MiB cache reuses only byte-identical, already verified encodings across ship companions. Decoding checks dimensions, pixel bounds, lossless bitstream type and absence of animation before allocating the output. Native and WASM use the same scalar encoder to keep published/host-generated identities consistent. Workshop restores PNGs when exporting editable content.

The manually invoked [image codec benchmark](smoke/lossless-images.md) compares the current representation with stronger raw compression, optimised PNG and exact WebP on shipped colour/normal/depth assets. Its timings are observations rather than CI thresholds.

## Validation

Synthetic production-loader cases cover ZIP/DAT equivalence, pixel preservation, editable imports, damaged/versioned input, dependent scenario packaging and Console selection isolation. Existing content, session, network, Workshop and WASM cases exercise their real loaders. Graphical loading, cancellation and file-picker checks are manually triggered evidence; headless tests do not establish reader, physical-device or performance acceptance.

Display request checks cover independent completion, retained content, cancellation/retry and stale success/error refusal. The manually invoked `phoenix_console_transition_smoke --loading-only` journey loads synthetic content through production paths and exercises a ready Console while another display prepares, cancels and retries. It also checks generation reuse and command revocation. See [screen-local loading evidence](smoke/screen-local-loading.md).
